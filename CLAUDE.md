# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Wildhaven is a single-player, top-down browser exploration game. It is still a prototype. On the selection screen the player picks one of three characters: Frontier Scout, Wandering Builder, or Shipwreck Survivor. Each one starts far from the others in one shared world of seven regions (desert, pine forest, snow, meadows, lagoon, canyons, jungle). The current milestone covers character selection, exploration, supply gathering, discovering regions, finding 52 landmarks, finding 14 signposts and fast-travelling between them, climbing hills by their stairs, and saving each character separately. It also covers **archipelago slice A1**: the home continent is an island in a sea border, with driftwood on its beaches, four old boats (one can be repaired), coastal sailing and three lagoon islets to reach. The archipelago design is `docs/superpowers/specs/2026-11-19-archipelago-design.md`; slices A2 to A4 (the big ship, a second continent, the archipelago map) are not built. The big world is build 1 of 4 in `docs/superpowers/specs/2026-11-19-big-world-design.md`; builds 2 to 4 (objectives journal and collectibles, harsh conditions and gear, locals) are not implemented, except a **prototype field journal for Pinefall Woods only** (a page, keepsake and trail clue per place; open with J). It exists to playtest whether finds that pay off make players chase the next place; the slice plan is `~/.gstack/projects/game 1/ryann-main-slice-plan-20261119-134500.md`. The long-term direction is a survival-and-settlement game with building, settlers, survival meters, and wolves. That design is in `docs/superpowers/specs/2026-11-19-survival-settlement-design.md`. Its **M2 "loop proof" is implemented** (`docs/superpowers/specs/2026-11-19-m2-loop-proof-design.md`): a 6-minute day/night cycle, health/hunger/warmth meters, campfires (B) that found named camps, a three-item needs list per camp that refreshes at dawn, passing out from cold, fog of war by walked area, herbal tea and healing, and regrowing supplies. **Tools and crafting are implemented** (`docs/superpowers/specs/2026-11-19-tools-crafting-design.md`, the gathering-tools piece of M3 pulled forward): every tree and rock in the map can be chopped (axe) or mined (pickaxe); stone tools (wood + stone, crafted anywhere, wear out) and iron tools (wood + stone + iron, forged with a hammer beside one of the player's campfires, last forever) are crafted from the Build menu. **Three villagers live and work in Hollowstead village** (`NPCS` in `src/data/npcs.js`: Maren the woodsworker, Bram the stoneworker, Tilly the grower): the same home spots around Hollowstead Square whichever character is played. Each has a list of `jobs`, best first; a job is done round and round: walk to `work`, do it (`chop` at the village's scrap timber, `mine` at its boulder, or `pickup` a load; `NPC_WORK_SECONDS`), carry the load to `drop`, set it down (`NPC_DEPOSIT_SECONDS`), rest `NPC_REST_MIN` to `NPC_REST_MAX` seconds. A job's `needs` names the supply it works on (`village-wood` for Maren's chopping, `village-stone` for Bram's mining): while the player has gathered it and it has not regrown, `pickJob` gives the next job (hauling: `pickup` at their pile, carry it somewhere else), and a villager on the way to that supply or working on it stops, rests `NPC_RETRY` seconds and picks again (`canDo`); one already carrying a load delivers it first. They go back to the first job after the supply regrows. The last job needs nothing. It is only a show: nothing is added to any stock and the load vanishes when set down. `src/actions/villagers.js` runs it (`tickVillagers`, called by the frame loop after `tickSurvival`; `planErrand`; `villagerFooting`): each walk is planned with `findPath` (the A* search in `actions/approach.js`, shared with the player's click to walk) round water, cliffs, buildings, standing trees, rocks and supplies, old boats and campfires; a blocked step slides along a corner like the player, and otherwise the villager waits `NPC_RETRY` seconds and plans again. A walking villager stops while the player is within `NPC_STOP` (110) units, so they never walk into the player; a resting one turns to look at a player within `NPC_NOTICE` (280), and the name shows then. They are solid where they stand now, but do not block each other. `src/world/npcs.js` holds `VILLAGERS` (the live positions and phases, kept in the module and **never saved**), `resetVillagers` (called when a game opens, so they always start from home), `npcFacing`, `villagerPose` (which sheet, picture and mirroring shows what one is doing) and `npcBases`, which `solidBases` includes. The renderer draws them from `assets/characters/settlers/` (`SETTLERS` in `sheets.js`; a row per villager): `idle` (a column per direction), `walk-south/east/north`, and the east-facing work sheets `carry`, `deposit` (played backwards for picking up), `chop` and `mine`, mirrored for west; a loaded villager therefore only faces east or west. `cuts` gives a sheet uneven column edges and `feet` anchors frames on the boots. There is no sowing, tending or harvesting art (only prompts), so nobody sows. They do not talk and cannot be recruited. Shelter, stockpile, farm, settlers, wolves and settlement tiers (the rest of M3) are not implemented. **Do not describe roadmap features as if they already exist.**

The standardized game design document is `docs/gdd.md` (imported 2026-11-19 with `/game-import`). It tags every item **[Built]** or **[Planned]**, records the audience (cozy survival), fantasy (exploration/discovery), retention hooks, and the hobby/no-monetization intent, and lists open spec-vs-build mismatches. When the GDD and the code disagree, trust the code.

```sh
node --test tests/actions/gather.test.js                              # one file
node --test --test-name-pattern="stale tab" tests/game/saves.test.js  # one test by name

python tools/prepare-generated-art.py     # key out the magenta of the Nano Banana art in source/originals/ and size it (then build-map.py)
python tools/make-biome-standins.py       # create any missing stand-in biome art (never overwrites)

```

Prettier 3 is the formatter (see Code Style below); there is no linter. Requires Node 20.19+ or 22.12+; the project was developed on Node 24.

Saves are scoped to the page's origin, so `127.0.0.1` and `localhost` are separate save locations. Do verification at `127.0.0.1` (the dev script's host) so it never overwrites the user's own saves on `localhost`.

## Tech Stack

Vanilla JavaScript ES modules, no framework. Vite 7 bundles the code and assets. Phaser 4 is used **only as the renderer**. HTML/CSS handle the UI and dialogs. Node's built-in `node:test` runs the tests. Prettier formats the code. Python (numpy, Pillow) builds the map offline.

**Keep the pure modules runnable in Node.** `data/`, `world/`, `actions/`, `game/` and `animation/clips.js` must not import `ui/`, `core/`, `render/`, `sheets.js`, `preview.js`, PNG or CSS files, and must not use `import.meta`, `document` or `window`. `tests/boundaries.test.js` enforces this. JSON is imported with `import ... with { type: 'json' }` so Node can read it.

**Adding an action:** add a file in `src/actions/`, bind its key in `src/core/input.js`, add a clip in `src/animation/clips.js` if it's animated, and add a test in `tests/actions/`.

**Shared session.** `core/session.js` `createSession()` holds what the browser layer shares: selected character, game state, animator, renderer, save session, current screen, held keys, and frame clock. `main.js` builds one `ui` object (`hud`, `dialogs`, `selection`, `input`) and passes `(session, ui)` to each module, so modules don't import each other in cycles.

**Input belongs to `core/input.js`, not Phaser.** Phaser's keyboard, mouse, and touch input are switched off. `core/input.js` tracks held keys in `session.keys`, the mouse over the world in `session.pointer` (for the build ghost), and exposes `moveIntent()`. Keys: E places the fire in build mode; otherwise it steps ashore, boards, repairs or gathers (`beginInteraction`), and with none of those in reach opens a camp beside your fire (on foot), and last of all says which tool a tree or rock in reach needs, B opens or closes the build menu (or leaves build mode), 1 picks the campfire, 2, 3 and 4 craft the axe, pickaxe and hammer and 5 to 8 make the torch, feather coat, antler grip and rowboat while the menu is open, F eat, H heal, M map, J journal, Escape pause (or close the build menu / leave build mode). The item box's food and herbs slots and the Build button do the same as F, H and B. **Click to walk:** every node can be hovered and clicked: a tree or rock shows its tool badge, and anything picked by hand (berries, small stones, flowers, driftwood, the fixed supplies) shows the resource it gives, with its hit box grown to at least `HOVER_MIN` (56 units) in `renderer.js` so small pictures are easy to point at. **Working position:** before any work on a thing in reach (picking by hand, chopping, mining, mending an old boat; by E, the interact button or a click), the player takes a short step to the spot beside it (`standSpot`/`beginPlacing` in `actions/approach.js`; `STAND_SIDE`, `STAND_GAP`, `STAND_INSIDE`, `STAND_FRONT`, `STAND_STUCK` in `balance.js`), because every working picture faces east or west. The spot is clear of a solid base and a little south of the thing's foot, so the player is drawn in front of a tree. The step is a `placing` walk the frame loop follows, and if it is blocked the work starts from where the player stands. While picking by hand the progress bar sits over the player's head, not over the low patch. Crafting has no target, so it happens where the player stands. A click on the node under the mouse gathers it when it is in reach; from farther away `clickNode` sets `session.walk` (never saved) and the frame loop's `followWalk` steers the player along the planned path and starts the action on arrival. A movement key, an action, the build menu or any dialog calls the walk off; a walk stuck for `APPROACH_STUCK` seconds plans once more, then gives up with a toast. Keys typed into a text box are ignored. The game counts as paused whenever any `<dialog>` is open (`ui.dialogs.isPaused()`), including the camp name, camp and pass-out dialogs. The simulation also stops while the tab is hidden.

**Frame loop (`core/loop.js`).** Each frame:
1. Clamp `dt` to 0.05.
2. If an action is running and a movement key is held, `cancelAction` (nothing is awarded).
3. Call `movePlayer`, then `tickSurvival` (world clock, meters, dawn update; returns events), `ui.build.update`, and `advanceAnimation`. The survival tick keeps running while the player is in the boat.
4. When a timed action *finishes*, call `finishInteraction(state, target)` (a repair, a gather, which wears a stone tool, or a `craft:<tool>` action) with the id it targeted. Pressing E only calls `beginInteraction`, which starts the clip for `gatherTime(state, node)` seconds (or `REPAIR_SECONDS`), so rewards are granted exactly once. While rowing, the loop also shows "Too rough for a small boat" when the boat pushes at deep water, at most every 4 s.
5. Run `discover` (finds also go through `markFinds` for camp needs), `revealAround` for the fog, and handle survival events: health at 0 starts the `collapse` action, and when it finishes the loop shows the pass-out screen (at once in the boat), whose closing calls `passOut`; other events become toasts; dawn saves. Then autosave every 10 s, call `renderer.draw(state, dt, animator, session.build)`, and refresh the HUD about every 0.12 s.

Because `dt` is clamped, game time runs slower than real time when the page renders below 20 fps (e.g. a hidden browser pane), and an action takes longer.

**Save model.** Each character has its own key, `wildhaven.adventure.v1.<characterId>`, and the save object is `version: 8` (`SAVE_VERSION` in `game/state.js`). Version 8 added `torch` (seconds left, 0 to `TORCH_SECONDS`), `coat` (boolean), a built boat's `from: 'built'` with `home`, and lets a stone tool hold up to twice a new one's uses; a **version 7** save goes through `addGear` (torch 0, no coat). Version 7 added the `feather`, `pinecone` and `antler` resources; a **version 6** save goes through `addFinds` (each starts at 0). Version 6 added `tools` (`{axe|pickaxe|hammer: {tier: 'stone', uses} | {tier: 'iron'}}`; a missing key means not owned) and the `iron` resource; a **version 5** save goes through `addTools` (iron 0, the character's kit tools). The save also holds the survival fields: `time` (the world clock, game seconds since the dawn of day 1; `elapsed` stays as time played), `meters` (`health`, `hunger`, `warmth`, 0-100), `tea` (seconds of tea left), `camps` (`{id: 'camp-<n>', name, x, y, grown, needs: [3 needs]}`) and `fog` (a hex string sized from the map); there is no `collected`: supplies regrow through `regrowAt`, measured on `time`. It also holds the boat fields: `wrecks` (the old-boat ids found), `boat` (`{from, x, y, dir}` or null) and `aboard`. **Older saves are upgraded, not reset.** A **version 4** save (the survival update, made before the sea border) goes through `addSeaBorder` (then `addTools`): the player, every camp, and wild-patch ids in `regrowAt` move out by `SEA_BORDER` (2048 units), and `growFog` re-indexes the fog onto the bigger grid (2048 is exactly 8 fog squares, `BORDER_SQUARES`), so every seen square moves 8 squares right and down and the new sea-border squares start unseen; a camp whose shifted spot is now sea is dropped, and the boat fields start empty. A **version 3** save goes through `upgradeV3` (then `addTools`), which does both steps: morning of day 1, timers keep their time left, collected supplies get a two-day timer, positions and wild-patch ids shift by `SEA_BORDER`, and the fog is lifted over discovered regions (not over the sea border) and around the player. In both, a player whose shifted spot is no longer walkable (cliffs ignored) goes to their character's spawn with progress kept. Version 2 saves, and the archipelago branch's never-released version 4 (boat fields but no survival fields), fail the checks and take the start-fresh path. A boat that is no longer on sea returns to its wreck's `launch` point (`placeBoat`). `restoreGame` validates the data strictly and *rebuilds* the object field by field. `restoreGame` drops `regrowAt` timers that have run out. A found id in `landmarks`, `waypoints` or `wrecks` that the map no longer has (a place deleted or renamed in the world editor) is dropped on load, not treated as a broken save; a mended boat whose old boat is gone is removed, and a player who was aboard it starts from their spawn. It checks an on-foot saved spot with `isWalkable(x, y, [], false, isSceneryNode)` (cliffs, trees and rocks ignored), so a save made where a hill now stands, or on a chopped tree's spot, still loads (`movePlayer` lets the player walk out of a tree that grew back); `movePlayer` then ignores cliffs until the player has walked off one. Camp spots are checked the same way. Adding a field to game state therefore means updating `createGame`, the checks in `restoreGame`, and the object it returns, or the field is silently dropped on load. If old saves can't be read safely, bump `version` and either upgrade the old shape or let old saves show the "could not be read, start fresh" path. `createSaveSession` remembers the last raw value it saw and refuses to write if storage has changed (`reason: 'conflict'`), so a stale tab can't overwrite a newer save. Saves happen on gather, repair, craft, discovery, signpost travel, boarding, landing, placing and naming a camp, every camp action (give, tea, eat, heal, rest), getting up after passing out, dawn, opening pause, hiding the tab, `pagehide`, and every 10 s. Separately, `readActive`/`setActive` keep the character being played in `sessionStorage` (`wildhaven.active`); on load `main.js` resumes it if that slot has a readable save, so a refresh returns to the game. Only the "Return to characters" and loading-screen "Back to characters" buttons clear it. Animation state is never saved, and a test checks this.

**Directions** are encoded everywhere (state, sprite columns, locomotion rows) as `0 = south, 1 = west, 2 = east, 3 = north`.

## World / Map Pipeline

```
assets/world/source/ground/{grass,dirt,soil,jungle,rock,snow,sand,water,deep}.png
assets/world/source/places.json  (regions, spawns, supplies, landmarks, waypoints, wrecks)
assets/world/source/edits.json   (objects removed and placed by hand in the world editor)
assets/world/source/terrain.json (ground painted by hand in the world editor)
assets/world/source/cliffs/<kit>.png + cliffs.json  (cliff pictures the hill tiles are cut from)
assets/world/source/shorelines/<kind>-bank.png + shorelines.json  (painted banks for the water's edge)
assets/world/source/objects/<kind>/*.png + objects.json  ──► tools/build-map.py ──► assets/world/map/
                                                                                   tileset.png
                                                                                   wildhaven.json  (Tiled format)
                                                                                   overview.webp   (minimap/world map)
```

- **World art is split into folders by kind.** `source/ground/` holds the nine ground textures (including `soil` and `deep`). `source/cliffs/` holds the three cliff pictures (`meadow`, `canyon`, `snow`) the hill tiles are cut from, and `cliffs.json`. `source/objects/` has one folder per kind of thing: `trees/`, `plants/`, `rocks/`, `buildings/` (houses, workshop, tent, ship, sandstone ruin) and `props/` (bridge, campfire, log, signpost). `source/originals/` keeps the full-size generated PNGs in the same kind folders. Every sprite's `kind` field in `objects.json` names its folder; `build-map.py`, `make-biome-standins.py` and `tests/world/nodes.test.js` find files through it. Everything else (the map, `places.json`, `SUPPLIES`, the renderer's `objectUrls`) names sprites by file name alone, so **a sprite name must be unique across all kind folders**. `tests/world/objects.test.js` checks this, and that every file is in the folder its entry names.
- To add an object sprite: save `<name>.png` and `<name>.prompt.txt` in the right kind folder, add a `<name>` entry with that `kind` to `objects.json`, and re-run `build-map.py`.

- `wildhaven.json` is the single source of truth for both rendering and collision. The map is 448×320 tiles at 64 px each (28,672×20,480 world units): the old 384×256 land plus a 32-tile sea border (`PAD` in `build-map.py`, map property `seaBorder`, `SEA_BORDER` in the game). Hand-written and random positions in `build-map.py` (rivers, coast, scenery, hills) are in land units; `places.json` is in world units. It has terrain tile layers `ground`/`dirt`/`soil`/`jungle`/`rock`/`snow`/`sand`/`water`/`deep` (bottom to top; `water` also paints tiles whose corners are all deep, so it marks all sea for collision, and `deep` marks only water more than 1,200 units from land, `DEEP_FROM`), a `cliffs` tile layer over them, and an `objects` point layer. The renderer reads the tile layer names from the map, so a new layer needs no code change. A terrain layer paints a tile only when one of the tile's corners is its own terrain, and then covers every corner of its rank or higher, so the lower terrain runs on underneath a shoreline. The map file's properties also hold the region grid (`regionCell`, `regionCols`, `regionGrid`: one digit per 256-unit square, the region's index in `places.json`) and the `elevation` grid (one letter per tile of the whole map: `0`–`3` level, `w` cliff wall, `s` stairs; the sea and the coast are `0`).
- Collision in `src/world/map.js` combines three sources. The water layer uses per-tile corner masks: the four corner values are blended, and a point counts as water at ≥0.35 (the corner-mask encoding is shared with `build-map.py`). `isSailable` (the boat's rule) is water ≥ 0.5, not deep, inside the world margin and not inside an object; `isDeep` reads the `deep` layer. `inland()` in `build-map.py` draws the wobbly coast with a 220-unit sand beach (`BEACH`). The overview is 1568×1120. Each object also has a solid base, its `footprint` in `objects.json`. And `hitsCliff` reads the elevation grid: a wall tile is solid, and a spot within `CLIFF_GAP` (20) units of a tile of another level is blocked unless one of the two is stairs. The blocked strip is 20 units on each side of an edge, wider than the longest step (24.5), which `tests/actions/move.test.js` checks. There are no hills at sea, so `isSailable` has no cliff check.
- **Banks ("bank tiles" in `build-map.py`).** A `banks` tile layer sits over `deep` and under `cliffs`: a painted strip 56 units wide (`BANK_LAND`) along every waterline, with a 7-unit wet edge past it (`BANK_WET`). There are three kinds, each cut from the straight piece of one sheet in `source/shorelines/` (`shorelines.json` says where): `ocean` round the sea and the lagoon (cut below its row of plants, because the beach is bare sand), `river` along the rivers, `lake` round the pools (`water_kind`). The strip repeats every 256 units and each tile bends it along its own shore: tile corners are numbered by distance from water (0 water, 1 touching, 2 farther), blended like the terrain masks, and the same noise as the water tile is added, so the bank's waterline is exactly the water tile's edge. Bank tiles are made only for the corner mixes the map really has (about 1,050), and the tileset is 62 tiles across so it stays under 4096 px. The layer is only a picture: collision still reads `water` and `deep`. The sheets' corner and curve pieces are not used.
- **Footpaths ("footpaths" in `build-map.py`).** Worn paths join the three starting places and the fourteen signposts into one network: the shortest set of links that reaches them all (a minimum spanning tree), each walked out by A* on the tile grid over dry, level tiles that are not under a hand-placed object or within 110 units of a supply, so a path crosses a river only at a ford or bridge and goes round hills. A later route pays less on tiles that already have a path, so routes merge into trunks. Each route is rounded and a piece is laid every 80 units (`PATH_STEP`): `path-dirt-a/b` in the green regions, `path-stone-a/b` in the desert, canyons and snow (`PATH_STONE`). `prepare-sprite-art.py` cuts the pieces from the straight module of `source/paths/path-dirt.png` and `path-cobblestone.png` (two windows each, both ends faded so pieces overlap without a seam); the sheets' bend, T and crossroads modules and the boardwalk and stepping-stone sheets are not used. The pieces are the map's only objects with a `rotation`; their `objects.json` entries have `path: true`, and the renderer turns them and draws them at depth -1.5, under the other flat things. Trees, rocks and flowers within 85 units of a path (170 to its south) are removed, and tufts, small stones, berries and sticks keep 60 away. Landmarks get no path on purpose. Paths are only a picture: no speed bonus, no collision. `tests/world/map.test.js` checks every piece is on dry, level, clear ground.
- **Water ripples.** `build-map.py` also scatters three flat animated sprites on open water (`RIPPLES`: `sea-wave`, `river-ripple`, `lake-ripple`), one seed per 120-unit square, never under a bridge. `prepare-sprite-art.py` cuts them from the three rows of `source/animations/water-ripples-loop.png`; their `animations.json` entries carry `loop` (frames a second), and the renderer plays any map object with `loop` round and round while its chunk is on screen (hidden with reduced motion).
- **Hills ("hills and cliffs" in `build-map.py`).** A hill is a stack of flat-topped levels on the tile grid, drawn in 2×2-tile blocks so every wall is at least two tiles wide. Each level's south edge drops down a wall `WALL_ROWS` = 2 tiles (128 units) tall; north, west and east edges show only a low lip, because the camera looks from the south. `HILL_RULES` says which regions get hills, which kit (`meadow`, `canyon`, `snow`) and how many levels; placement uses one random seed per 1,600-unit square, with a few retries, and keeps every hill 4 tiles from places (old boats included), hand-placed objects and fords, off dirt and any water (river, pool or sea, shallow or deep), inside one region and 5 tiles from other hills. Hills are placed in land units on the old land's 384×256-tile grid, with the seeds they had before the sea border, so each stands on the same spot of land; the grids are then padded with 32 tiles of level-0 sea on every side ("elevation grid" in `build-map.py`). Every level gets one two-tile flight of stairs on its southernmost edge, drawn as a flat `<kit>-stairs` object. The `cliffs` tiles are painted from strips cut out of `source/cliffs/<kit>.png` (where things sit in each picture is in `cliffs.json`): the repeating wall, its two end pieces, and the side lips; each higher level also gets a little warm light so it reads as higher. Scenery and ground detail are kept off walls, edges and stairs (`on_flat`). `tests/world/cliffs.test.js` checks walls are solid, edges block, every flight climbs, and every level of every hill can be reached on foot.
- `objects.json` fields: `kind` is the folder under `objects/` that holds the sprite. `origin` is the ground contact point as a fraction of the sprite size. `footprint` is `[halfWidth, depth]` of the solid base; leave it out for walk-through objects. `flat` means the object is drawn under characters. `scale` is the draw size wherever the map places that sprite (flowers use 0.4 so a patch is smaller than a character); the footprint scales with it. Every other object is depth-sorted by its y position, so the player can walk in front of or behind it.
- **`assets/world/source/places.json` is the single source for positions.** It holds the regions, spawns, supply spots, landmarks, waypoints and `wrecks` (each a beach point plus a `launch` water point, which lies outside the 130-unit dry circle). `build-map.py` reads it to shape the land (water is pushed back from every listed point, scenery is kept 150 units away and never stands just south of a point, a landmark's `object` sprite stands 60 units north of it, a `pool` is dug north of it, each signpost stands 50 units north of its waypoint). `src/data/places.js` exposes the same file to the game. To move or add a place, use the world editor (`/editor.html` in `npm run dev`), or edit the JSON and re-run the script; `tests/world/places.test.js` then checks every point is walkable, in its named region and reachable on foot.
- **`assets/world/source/edits.json` holds hand edits to the map's objects** (world editor, Objects mode): `removed` lists generated objects to leave out and `added` lists objects placed by hand, each `{name, x, y}` in world units. `build-map.py` applies it last ("hand edits"), after every scatter pass, so an edit never reshuffles anything else, and nothing is cleared around an added object. Path pieces, hill stairs, ripples, signposts and bridges can't be named in it (`editable` in the script, `lockReason` in `src/editor/edits.js`). A removal that matches nothing is listed in the map's `staleEdits` property. `tests/world/edits.test.js` fails if the map was not rebuilt after the file changed.
- **`assets/world/source/terrain.json` holds hand-painted ground** (world editor, Terrain mode): `ground` is a list of runs `[row, firstColumn, lastColumn, kind]` of tile **corners** (rows 0 to 320, columns 0 to 448; kinds `grass`, `dirt`, `soil`, `jungle`, `rock`, `snow`, `sand`, `water`). In `build-map.py`, `terrain(x, y)` asks these overrides first (the nearest corner) and falls back to `generated_terrain`, so banks, deep sea, collision, scatter and hills follow a painted coast; painted water within 130 units of a place still becomes sand. Land may not be painted within 20 tiles of the map edge (`EDGE_SEA` in the script and in `src/editor/terrain.js`): water within 1,200 units of land is shallow, and the outer sea must stay deep. The map stores the generated ground per corner (`baseGround`) and a fingerprint of the file it was built from (`terrainHash`); `tests/world/terrain.test.js` fails if the map was not rebuilt after the file changed. Scenery near painted ground is re-scattered by the rebuild; objects placed by hand are not.
- **Regions, rivers and scenery are defined in `build-map.py`.** `LAYOUT` is an 8×8 grid of region letters whose borders are warped by sine waves. `RIVERS` are polylines of water; `FORDS` are the crossing points (dry ground within 190 units) and `BRIDGES` add a plank deck. Scenery is scattered with **one random seed per grid square**, so changing one part of the map never reshuffles another part. The placement of landmark buildings (tent, houses, workshop, ship) is relative to the spawns.
- **Supply nodes are not in the map.** `src/render/renderer.js` draws each one from `NODES` (`src/world/nodes.js`) (`sprite` is an `objects.json` key, drawn at `scale`), and `nodeBases` in `src/world/nodes.js` makes its scaled footprint solid while it stands (`goneSupplies`); `solidBases` adds old boats on the beach and campfires. `movePlayer` ignores a base the player is already inside, so an old save can't get trapped.
- **Wild scenery is in the map and also harvestable.** `WILD` in `src/data/supplies.js` names scattered sprites (`flowers`; `driftwood`, which gives 1 wood, regrows in 180 s and is scattered on sea beaches; and `pebbles`, "Small stones": about 670 little piles scattered over all the land by their own pass in `build-map.py` (`PEBBLES`), each giving 1 stone to bare hands and regrowing in 180 s, so a first pickaxe and campfire never wait on the few fixed stone supplies; and `wild-berries`: about 285 small walk-through berry bushes in the green regions (`BERRIES`; none in the desert, snow or canyons), each giving 1 food and regrowing in 180 s; and `sticks`: about 340 small piles of fallen branches in the wooded regions (`STICKS`; none in the desert, the canyons or on beach sand), giving wood to bare hands and regrowing in 180 s) that become `NODES` entries with id `<name>-<x>-<y>` and a `regrow` time. The renderer skips them in the scenery loop and draws them with the supplies. They are walk-through (no footprint), so `nodeBases` covers only the fixed `SUPPLIES`. `HARVEST` names the trees and rocks a tool can harvest; they become `NODES` too (`inScenery: true`), but the renderer keeps them in the scenery loop and their solid base is the map's own obstacle box, which `movePlayer` skips while the node is gone. Old boats are not in `NODES`; `wreckBases` makes each solid until it is repaired, and the renderer draws them.
- `tools/make-standin-art.py` cut placeholder source art out of `assets/world/wildhaven.png`. **Do not re-run it.** It would overwrite any source art that has since been replaced. It also predates the kind folders and still writes to the old flat paths. To change art, replace the file under `source/ground/` or `source/objects/<kind>/` and re-run `build-map.py`.
- `tools/make-biome-standins.py` derives the snow, rock, jungle and deep-sea textures and the biome and boat sprites (twelve biome sprites, plus `driftwood`, `old-boat` and `rowboat` for slice A1) from existing art. It skips any file that already exists, so it is safe to re-run. Each stand-in has a `.prompt.txt` for generating the real art.

## Character Sprites

- Every sheet the game loads sits in the character's own folder, `assets/characters/<id>/` (`scout/`, `builder/`, `survivor/`), and is listed in `SOURCES` in `src/animation/sheets.js`.
- `<id>/<id>-idle-v1.png` is one row of 4 standing poses, one per direction. It is also used through CSS for the selection-screen figure and the HUD portrait (the "Character idle sheets" rules in `src/style.css`).
- `<id>/<id>-side-walk-v2.png` is one row of 4 frames walking east, mirrored for west, with each frame anchored on the head to prevent sliding (`steadyAnchors`).
- The idle and side-walk sheets were generated as one picture of all three characters. Those originals and their prompts are kept in `assets/characters/originals/`; `python tools/split-character-sheets.py` cuts them into the per-character copies (it overwrites the copies). Because they were painted together, every character's idle and side-walk poses are sized by the scout's row (see `loadCharacterSheets`), so their relative heights match the painting.
- `<id>/<id>-locomotion.png` has 8 rows (walk S/W/E/N, then run S/W/E/N) with 4 frames each. `<id>/<id>-run-v2.png` has 3 rows (south, east, north) of 6 frames. `<id>/<id>-actions.png` has 5 rows (gather, build, craft, fight, swim). The action art faces east and is mirrored for west.
- The row boundaries are measured **`edges`** arrays in `SOURCES` in `src/animation/sheets.js`, not equal-height rows. If you regenerate a sheet, re-measure its edges. Columns are equal quarters of the sheet width. Within each cell the frame bounds come from pixels with alpha > 40.
- `<id>/<id>-idle-loop.png` has 4 rows (south, west, east, north) of 4 breathing frames; it is the `idle` clip, played in the `order` in `CLIPS` so the blink frame shows once per loop. `<id>/<id>-chop.png` is one row of 4 east-facing axe frames (the `chop` clip, mirrored for west). Both were painted per character at their own size, so `loadCharacterSheets` sizes them from the old idle pose.
- **Diagonal walk and run.** `assets/characters/diagonal/` holds all-character `walk-ne`, `walk-se` (4 frames) and `run-ne`, `run-se` (6 frames) pictures; `split-character-sheets.py` cuts them into `<id>/<id>-walk-ne.png` and so on (sheets `walkNE`, `walkSE`, `runNE`, `runSE`; the run rows are 341/342/341 px tall, so their `edges` differ per character). The west diagonals mirror the east art. `state.player.direction` stays 0 to 3 (saves are unchanged): the loop works out `diagonalOf` from how far the player really moved this frame, `advanceAnimation` keeps it in `animator.diagonal` only while moving, and `sampleAnimation`/`resolvePose` take it as their last argument. Standing still after a diagonal shows the north or south idle.
- **Survival state sheets.** `assets/characters/states/` holds all-character pictures (4 frames across, a row per character, facing east) with their prompts; `python tools/split-character-sheets.py` cuts them into `<id>/<id>-sleeping.png`, `-waking-up.png`, `-hungry.png`, `-damage-hunger.png`, `-damage-cold.png` and `-damage-attack.png`. Their clips are `sleep`, `wake` (a timed action with no target), `hungry`, and the `reaction` clips `hurtHunger`, `hurtCold`, `hurtAttack`. `startSleep`/`wakeUp` in `clips.js` lay the character down for a 2 s nap after resting, and show them getting up by the fire once the pass-out screen is closed; `advanceAnimation` takes `hungry` (hunger below `HUNGRY_BELOW`) and `hurt` (picked by `hurtClip` in `core/loop.js`: `hurtCold` while freezing, else `hurtHunger` while starving) and replays a reaction every `every` seconds. Starving drains health slowly (see Meters). `hurtAttack` is preview-only (nothing attacks yet). **Collapse.** `<id>/<id>-dying-v2.png` (sheet `dying`: one row of six 336×320 cells, facing east, packed by hand from `states/dying-v2.png`; `states/dying-v2.manifest.json` says from where, and `split-character-sheets.py` does not cut it) is the `collapse` clip, a `once` action: it plays through one time, holds its last picture (also after it finishes) and can't be cancelled (`cancelAction` refuses). When health reaches 0 on foot, `handleSurvival` in `core/loop.js` calls `startCollapse`, and when the `COLLAPSE_SECONDS` = 1.8 s action finishes the loop only opens the pass-out screen (`ui.camp.showPassOut`), over the character lying where they fell. **The scene changes only when that screen closes** ("Get up" or Escape): `getUp` in `ui/camp.js` then calls `passOut` (midday, the move to a fire), resets the camera, plays `wake`, saves, and toasts a boat that drifted home or camps with new needs. The check reads the health itself, not only the `passout` event, so a save made mid-fall or with the screen open (health still 0) passes out again after loading. In the boat there is no fall: the screen comes at once. The four-frame `states/dying.png` is not used.

Fight and swim exist only in the preview dialog and must not imply working mechanics. The `holding-tools` and `rowing` sheets are not loaded: owning a tool doesn't change the character's pose, and the boat has no rowing pose yet.

## Game Rules That Affect Code

- There are eight resources (`RESOURCES`): `wood`, `stone`, `food`, `herbs`, `iron`, and the three finds `feather`, `pinecone`, `antler`. The finds are picked up from the ground (`feather`, `pine-cone` and `antler` patches in `WILD`, scattered by the `FINDS` pass in `build-map.py` with three loose stones, `mossy-stone`, `grey-rock` and `flat-stone`, which give plain stone), and a chopped map tree drops one 2 times in 10 (`DROP_CHANCE`; `TREE_DROPS`: a cone from pines, a feather from leafy trees and palms; `dropFrom` in `actions/gather.js`, reported as `drop` by `finishInteraction`; the hand-placed pine supply and the fallen log drop nothing). The finds are spent on **gear** (below); camp needs never ask for them. `RESOURCE_NAMES` gives a resource its words in a message ("pine cone"). They are always non-negative integers, and `restoreGame` rejects anything else. Herbs come only from wild flowers; they are spent on healing (3 herbs, +30 health) and tea (5 herbs). Food is eaten for +25 hunger; wood and stone build campfires (3 wood + 2 stone), mend an old boat and fill camp needs; iron, mined only from iron-streaked rocks (`cliff-rock` in Stonewater Canyons, `ice-rock` in Frostpeak), goes into iron tools. Camp needs never ask for iron (`needs.js` picks from the `NEED_AMOUNTS` keys).
- **Gear** (`GEAR` in `src/data/gear.js`, `GEAR_RECIPES` in `balance.js`, rules in `src/actions/gear.js`: `canMake`, `beginMake`, `finishMake`): four things made from the Build menu's Gear group (keys 5 to 8), each a timed action with the target `craft:<id>` that `finishInteraction` hands to `finishMake`. **Torch** (1 wood + 2 pine cones, anywhere): `state.torch` holds its seconds left (`TORCH_SECONDS` = 90); it burns down all the time, holds the cold off like tea (and is used before the tea), widens the glow around the player at night (`TORCH_LIGHT`), and `tickSurvival` reports `torchOut`. **Feather coat** (10 feathers + 2 antlers, beside one of the player's fires): `state.coat` is true for good and every cold drain is multiplied by `COAT_COLD` = 0.5; it is the first winter gear. **Antler grip** (1 antler): the most worn stone tool (`gripTool`, by share of a new tool's uses) gets a new tool's uses back, up to `GRIP_MAX` = 2 times a new one's. **Rowboat** (30 wood + 6 iron; a first-pass recipe that will also need nails once those exist): built on foot with sailable water within `BOARD_RANGE` (`launchSpot`), with the `build` clip for `REPAIR_SECONDS`; the boat is `{from: 'built', home: {x, y, dir}, x, y, dir}` (`BUILT` in `actions/boat.js`) and drifts back to `home`, not to an old boat. One boat per character still holds. No gear is made from the boat. Gear has no painted pictures: the menu rows borrow the finds' item pictures and the rowboat sprite, and the character's look does not change.
- Boat rules (`src/data/balance.js`): repairing an old boat costs 6 wood + 2 stone and takes 8 s (`REPAIR_SECONDS`), a character owns one boat, the player boards within 160 units (`BOARD_RANGE`) and lands within 160 (`LAND_RANGE`), the boat moves 210 units/s (300 with Shift), deep water blocks the small boat, and travelling to a signpost sends the boat drifting back to its old boat's `launch` spot (`sendBoatHome`, so a boat left at an islet is never lost; the map's travel toast says so) while the player arrives on foot. Old boats are found within 200 units like landmarks. Campfires can't be built from the boat (`checkPlacement` says "Step ashore to build", and the build menu won't open). Passing out while aboard wakes the player on foot by the nearest fire (or spawn), and the boat drifts back to its old boat's `launch` spot (`sendBoatHome`).
- `tests/world/flood.js` is a shared test helper, not a test file. `places.test.js` and `sea.test.js` use it to flood-fill what can be reached on foot or by boat.
- Fixed supplies (`SUPPLIES`, the first nine `NODES`) grow back `SUPPLY_REGROW` = 720 game-seconds (two in-game days) after gathering; wild patches grow back 180 game-seconds later (flowers give 2 herbs, beach driftwood 1 wood, small stones 1 stone, wild berries 1 food). `state.regrowAt` maps a gathered node's id to the `state.time` it returns, so regrowth stops when the game is paused or the tab is hidden. A supply's solid base exists only while it stands (`goneSupplies`). On load, `restoreGame` drops timers for patch ids the map no longer has and caps each timer at one `regrow` ahead. Both rules are availability checks in `isAvailable`. A node is gatherable within 95 units. A region (`REGIONS`) is discovered by standing in it; every spot in the world is in exactly one. A landmark is found within 200 units (`LANDMARK_RADIUS`) and a signpost within 110 (`WAYPOINT_RADIUS`). `travelTo` only moves the player to a signpost already in `state.waypoints`.
- Movement speed is 155 units/s walking and 245 units/s with Shift. Collision is checked separately on the x and y axes so the player slides along obstacles.
- Hills are climbed only by their stairs: walls and the edges between levels block movement. Height has no other effect yet (no view, speed or discovery bonus).
- Every gather is a timed action read through `gatherTime(state, node)`, and its clip loops for the whole time. Bare-hand gathers take `GATHER_SECONDS` = 6 s; a gather that needs a tool takes `TOOL_SECONDS` (5 s stone, 3 s iron). This is a design decision: tools shorten gathering, so don't shorten the base time as a "fix." A fresh movement press cancels the action and awards nothing. Key-repeat from a key that was held when E was pressed does not cancel it. Pause and a hidden tab freeze it.
- **Tools** (`TOOL_RECIPES`, `TOOL_USES` in `balance.js`): stone axe 3 wood + 2 stone, stone pickaxe 3 wood + 3 stone, stone hammer 2 wood + 3 stone (25, 25 and 10 uses; crafted anywhere); iron axe 2 wood + 1 stone + 3 iron, iron pickaxe 2 wood + 1 stone + 4 iron, iron hammer 2 wood + 1 stone + 3 iron (last forever; need a hammer and must be crafted inside one of the player's fires' warmth). A craft takes `CRAFT_SECONDS` = 3 s; moving cancels it and nothing is spent; `finishCraft` re-checks and pays in one step. Owning a tool is enough to use it; the player holds one of each, iron replaces stone, and a stone tool can be crafted again only after it breaks. A finished gather with a stone tool costs one use (warning at `TOOL_WEAR_WARNING` = 3 left; the last use still pays out), and forging iron costs a stone hammer one use. The Scout starts with a stone axe (the hatchet) and the Builder with a stone hammer; the Survivor starts with no tool but the fullest backpack (4 wood, 2 stone, 6 food: enough for a first campfire). Every map tree needs an axe (7 wood, or 10 from a pine cluster, big oak or jungle tree) and every rock a pickaxe (2 stone from rocks, 10 from a big boulder, or 1 iron); so does the Pinefall pine supply (7 wood). Logs are chopped like trees: the map's fallen log (`log` in `HARVEST`, 4 wood) and the two log supplies (`village-wood`, `coast-wood`, 4 wood each) need an axe; only beach driftwood and the scattered `sticks` piles give wood to bare hands. The three stone supplies (`camp-stone`, `village-stone`, `coast-stone`: "Small boulder", "Beach boulder", 5 stone each) need a pickaxe; for stone, only the scattered small stones (`pebbles`) are picked up by hand. A chopped tree or mined rock is walk-through until it regrows after `HARVEST_REGROW` = 1,080 game-seconds, but a campfire may never stand on its spot, and `NODE_CLEARANCE` applies only to supplies and flower patches. `tests/data/ladder.test.js` checks every tool is reachable from each character's start.
- When a node is in reach, its sprite glows (Phaser Glow filter, WebGL only) and an E key cap floats over it. A progress bar replaces the cap while the action runs. Gathered sprites fade out, and regrown patches fade back in; there is no stump or bare-bush art yet. Trees and rocks stay in the chunk-culled scenery; the renderer fades them by id (`harvest`, `harvestChunks`). Beside a tree or rock whose tool the player lacks, the interact button is faded ("Chop pine tree — needs an axe") and the node gets no glow.
- **Day and night.** `state.time` drives a 360 s day: dawn 0-20, day 20-210, dusk 210-240, night 240-360; a new game starts at 20. Resting (from dusk, at a camp) skips to the next dawn; passing out skips to the next midday (120). Both drain hunger for the skipped time and run the dawn update. Night is drawn nearly black on purpose (`NIGHT_DARK` = 0.94 and `DUSK_DARK` = 0.5 in `world/clock.js`): away from a fire only the small glow around the player is lit. The Canvas fallback, which can't cut lights, stops at 0.6 (`FLAT_DARK` in `lighting.js`).
- **Meters** (`tickSurvival`): warmth +20/s by a fire, +4/s by day, held at dusk, −100/60 per s at night away from a fire (×1.5 when starving) unless `tea` > 0; in a snowy region (`SNOW_REGIONS`, Frostpeak; `inSnow` in `world/regions.js`) warmth drains at every hour, ×1.5 of the night rate by day and dusk (`SNOW_COLD`) and ×2.5 at night (`SNOW_NIGHT_COLD`), and tea holds it off there too (winter gear is planned, not built); health −100/30 per s while freezing (no warmth, away from a fire, at night or in the snow), +2/s by a fire when fed, −100/240 per s while starving but never below 25 (`STARVE_FLOOR`: hunger alone can't cause a pass-out); hunger −100/720 per s. Health at 0 → the character collapses for 1.8 s, the pass-out screen opens, and closing it runs `passOut`: wake at the nearest fire (or spawn) at midday with 50 health; nothing is taken.
- **Campfires and camps.** Cost 3 wood + 2 stone, within 300 units of the player, base clear of water, scenery, supplies, other fires and the player, no node within 80, at least 3,000 from another camp, at most 50 camps. Warmth radius 260 + 40 per met need (max 10). Each camp has three needs (bring resources / find a place in the nearest other region with unfound places / find a new signpost on odd days); finds tick off via `markFinds`, resources via the camp dialog; met needs are replaced at dawn.
- **Fog.** 256-unit squares, uncovered within 1,000 units of the player every frame (`revealAround`); the maps draw unseen squares as solid fog, and region names show only once discovered.
- Balance numbers live in `src/data/balance.js` (speeds, reach, `GATHER_SECONDS`, landmark and signpost radii, the boat numbers (`REPAIR_COST`, `REPAIR_SECONDS`, `BOAT_SPEED`, `BOAT_FAST_SPEED`, `BOARD_RANGE`, `LAND_RANGE`, `DEEP_LOOKOUT`) and all of the M2 numbers above). Don't hardcode tuning numbers in actions.

## Code Style (repo rule)

This is a rule, not a preference. Code here should read easily for a beginner. Every change must follow it, and `npm run format:check` and `npm test` enforce most of it.

- **Prettier formats all code.** Run `npm run format` after editing; `npm run format:check` must pass. The settings in `.prettierrc.json` are single quotes, 100-column lines, and each file's existing line endings (this is a Windows checkout with `core.autocrlf`). `.prettierignore` leaves out `assets/` (generated or read by `build-map.py`), Markdown and `docs/`, `.claude/`, and build output. Don't hand-format against Prettier.
- **Every named function has a comment directly above it, written ELI5-style.** Use plain words a beginner understands and short sentences. Explain any jargon. Add an everyday comparison when it really helps (a backpack for resources, a stopwatch for timers), but don't be cutesy and don't label it "ELI5". Use a `/** ... */` block:
  - first line: what it does, in one simple sentence;
  - then a short plain-language explanation of how or why;
  - then `@param {type} name - meaning` and `@returns {type} meaning`, in plain words.

  A tiny one-line helper can have a one-line `/** ... */`. "Named function" means function declarations (inner ones too), `const name = (...) =>`, class and object methods, object properties holding arrow functions, and classes. Anonymous inline callbacks such as `.map((c) => ...)` are exempt unless their logic is non-obvious; then put a `//` line above. `tests/comments.test.js` fails when a named function has no comment on the line right above it.
- **Keep the *why*.** Comments that record why a decision was made stay. Examples are the per-square scatter seed, the clamped `dt`, and the 6 s `GATHER_SECONDS`. Reword them more simply if needed, but never drop the fact.
- **Headers and data.** Each file opens with a 2–4 line `//` header saying what it is for. Constants and data tables say what they hold and what each field means.
- **Spacing.** Put one blank line between top-level declarations and between functions. Inside longer function bodies, put blank lines between steps (setup, checks, work, return), with a short `//` comment on any step that isn't obvious. Short 2–4 line bodies stay tight.
- **HTML in template strings** is marked `/* HTML */` so Prettier formats it too. Prettier keeps inline tags touching by breaking lines as `</button` + `>`. Don't "tidy" those breaks: real whitespace there would add gaps between buttons.
- **Pure modules** (`data/`, `world/`, `actions/`, `game/`, `animation/clips.js`): comments must not contain the words `document`, `window` or `import.meta`, because `tests/boundaries.test.js` scans the whole file, comments included.
- **Tests:** each file has a header, and each `test(...)` has a `//` line above it saying what could break that it guards against.
- **Python in `tools/`:** a `#` comment above each `def`, not a docstring, so one-line defs stay one line. Prettier doesn't format Python.
- **CSS:** section headers (`/* ---- Name ---- */`) grouped by what's on screen, plus a note on any rule that isn't obvious.

Example of the expected tone and shape (`src/actions/move.js`):

```js
/**
 * Moves the player one small step in the direction the keys point.
 *
 * Think of the player as a toy on a table: each frame we nudge it a little. If a tree or the
 * sea blocks one direction, the toy still slides along the other one instead of stopping dead.
 *
 * @param {object} state - The game being played. Its `player` position and `distance` change.
 * @param {number} dx - Left/right push: -1 is west, 1 is east, 0 is neither.
 * @returns {boolean} True if the player really moved, so a blocked step shows the idle pose.
 */
```

## Conventions

- Nano Banana (Gemini) cannot paint real transparency, so its sprites are drawn on flat magenta. The full pictures go in `source/originals/<kind>/<name>.jpg` with their prompts, and `python tools/prepare-generated-art.py` keys out the magenta, trims, sizes and saves the game files (grass tufts, the dirt patch, the soil texture, the cliff pictures and the stairs sprites). Add a new picture to its lists before running it.
- Every generated art asset sits next to a `.prompt.txt` holding its exact generation prompt. Keep the original PNGs, and add a prompt file for any new generated art. The asset inventory is in `docs/art-direction.md` and `assets/characters/README.md`.
- Any failure while loading assets must end on the loading screen's retry state, never an endless loader. Image loads have timeouts (`loadImage`, plus the 20 s Phaser scene timeout).
- Keep `prefers-reduced-motion` support. It turns off camera smoothing, CSS transitions, and preview autoplay.
- Desktop keyboard and mouse is the primary target. Layouts must still work at about 390 px wide, where on-screen touch movement buttons appear.
- The main menu (`#selection`) must stay exactly `100svh` with no scrolling at any size from 320×480 up. Under 700 px wide it shows one character panel at a time.
- Feature plans go in `docs/superpowers/plans/`, and browser verification notes go in `docs/verification.md`.

## Verifying a Change

- `npm test`, `npm run build` and `npm run format:check` must all pass. `npm test` includes the comment rule (`tests/comments.test.js`) and a flood fill of the whole world (`tests/world/places.test.js`), so a map change that seals off a spawn, landmark, signpost or supply fails the tests.
- Unit tests don't cover rendering, input, animation, the map, or the UI. If you change any of those, start the game from the `wildhaven` launch config and play through with each affected character. Check the browser console for errors. If layout changed, also check the page at about 390 px wide. Add notable checks to `docs/verification.md`.
